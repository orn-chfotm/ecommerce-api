# CMS 구현 계획

- 작성일: 2026-09-10
- 상태: 구현 전 설계 문서
- 이번 작업 범위: 대화 내용을 문서화한다. 애플리케이션 코드, DB, 설정은 변경하지 않는다.

## 1. 목적과 설계 상태

공통 코드 관리를 시작으로 상품, 콘텐츠 페이지, 메뉴, 관리자 권한 관리가 추가될 수 있는 CMS 백엔드 구조를 정리한다.

CMS는 관리 기능을 제공하는 수단이며, 도메인은 관리 대상별로 구분한다. 모든 대상을 `code`나 `cms` 패키지 아래에 모으지 않는다.

| 구분 | 내용 |
| --- | --- |
| 대화에서 정리한 방향 | 공통 코드는 `CodeGroup`과 `CodeDetail`로 분리하고, 추가 depth는 상세의 자기참조로 표현한다. |
| 대화에서 정리한 방향 | 그룹 선택 후 최상위 상세를 조회하고, 상세 선택 시 자식 목록을 조회한다. |
| 대화에서 정리한 방향 | 상품, 페이지, 메뉴, 권한은 공통 코드와 별도 도메인으로 관리한다. |
| 기본 제안 | 코드 식별자와 소속 그룹은 고정하고, 상세는 삭제 대신 비활성화한다. |
| 후속 검토 (초기 범위 제외) | enum 표시 정보를 운영자가 편집해야 할 때 별도 표시 정보 모델을 검토한다. 초기에는 `systemCode`나 enum 항목의 DB 복제를 도입하지 않는다. |
| 후속 검토 (초기 범위 제외) | 추가 속성은 실제 사용처와 타입을 확인한 뒤 설계한다. `extraValue1`, `extraValue2` 같은 범용 확장 필드는 도입하지 않는다. |
| 후속 검토 (초기 범위 제외) | 고객용 조회 API와 성능 요구가 생기면 캐싱을 검토한다. 초기 조회는 DB를 사용하며, 캐싱 도입 시 별도 서버 간 무효화까지 설계한다. |
| 후속 결정 필요 | 관리자 역할 운영 정책, 메뉴별 요구 권한, 페이지 편집 기능, 상품 카테고리 전환 시점. |

## 2. 현재 구조와 디렉토리

현재 프로젝트는 `core`, `domain`, `infra`, `admin-api`, `user-api`의 5개 Gradle 모듈로 구성된다.

- `domain`: 엔티티, 서비스, DTO, 예외, Repository 포트.
- `infra`: JPA Repository, QueryDSL 조회, Repository 어댑터.
- `admin-api`: CMS 관리 API와 관리자 인증·인가 연결.
- `user-api`: 고객에게 필요한 데이터 조회 API.
- `core`: 감사 시간, 공통 응답, 공통 보안 등 기반 기능.

Repository 포트는 기존처럼 순수 인터페이스로 두며, `domain`에서 `JpaRepository`를 직접 상속하지 않는다.

```text
domain/src/main/java/com/build/ecommerce/domain/
  code/
    entity/
      CodeGroup.java
      CodeDetail.java
    repository/
    service/
    dto/
      request/
      response/
    exception/
  menu/
  authorization/
  admin/                 # 기존 관리자 계정
  product/               # 기존 상품 도메인 활용
  productcategory/       # 카테고리 전환 시 추가
  page/                  # 콘텐츠 요구 확정 후 추가

infra/src/main/java/com/build/ecommerce/infra/persistence/
  code/
  menu/
  authorization/

admin-api/src/main/java/com/build/ecommerce/adminapi/controller/
  CodeGroupController.java
  CodeDetailController.java
  MenuController.java
  RoleController.java
  ProductController.java # 기존 컨트롤러 활용
```

새 도메인은 기존 `entity`, `repository`, `service`, `dto`, `exception` 패턴을 따른다. 실제 구현 단계에 필요한 패키지만 생성한다. 상품 CMS 전용 엔티티나 별도 CMS Gradle 모듈은 만들지 않는다.

문서 작성 시 `domain/code/enetity` 아래에 비어 있는 `CodeGroup.java`, `CodeDetail.java`가 존재한다. 해당 파일은 이번 작업에서 수정하지 않는다. 이후 구현 시 패키지 이름은 기존 관례인 `entity`로 맞춘다.

## 3. 공통 코드 관리

### 엔티티

두 엔티티 모두 기존 `BaseTimeEntity`를 상속하여 등록·수정 시간을 관리한다. ID 생성은 기존 코드의 `GenerationType.IDENTITY` 방식을 따른다.

| 엔티티 | 필드 | 의미·기본 제안 |
| --- | --- | --- |
| `CodeGroup` | `id` | 그룹 PK |
| `CodeGroup` | `code` | 업무 식별자, 전체 유일, 생성 후 고정 |
| `CodeGroup` | `name` | 그룹 표시명 |
| `CodeGroup` | `sortOrder` | 그룹 표시 순서 |
| `CodeDetail` | `id` | 상세 PK |
| `CodeDetail` | `codeGroup` | 소속 그룹 FK, 필수, 생성 후 고정 |
| `CodeDetail` | `parent` | 바로 위 상세 FK, 최상위이면 null |
| `CodeDetail` | `code` | 그룹 내 유일한 업무 식별자, 생성 후 고정 |
| `CodeDetail` | `name` | 상세 표시명 |
| `CodeDetail` | `sortOrder` | 같은 부모 아래 형제 항목의 표시 순서 |
| `CodeDetail` | `active` | 신규 선택 가능 여부, 생성 시 true 제안 |

`CodeDetail.codeGroup`과 `CodeDetail.parent`는 지연 로딩하는 `ManyToOne` 관계로 구성한다. 그룹이나 상세에 역방향 컬렉션은 우선 두지 않고 Repository에서 필요한 목록을 조회한다. `depth`는 부모 관계로 알 수 있으므로 별도 저장하지 않는다.

```text
CodeGroup: INQUIRY_TYPE
  CodeDetail: PRODUCT       parent = null
    CodeDetail: RESTOCK     parent = PRODUCT
  CodeDetail: DELIVERY      parent = null
    CodeDetail: DOMESTIC    parent = DELIVERY
      CodeDetail: DELAY     parent = DOMESTIC
```

### 제약과 변경 정책

- DB에 그룹 코드의 유일 제약과 `(CODE_GROUP_ID, DETAIL_CODE)`의 복합 유일 제약을 둔다.
- 부모와 자식은 같은 그룹에 속해야 한다. 자기 자신이나 자신의 하위 항목을 부모로 지정할 수 없다.
- 이름, 정렬 순서, 활성 여부를 수정할 수 있다. 부모 변경을 제공할 때도 그룹 일치와 순환 검증을 수행한다.
- 부모 FK만으로는 순환과 그룹 불일치가 방지되지 않으므로 서비스에서 검증한다. 동시 구조 변경에도 불변식이 유지되도록 그룹 단위 변경 직렬화를 구현 시 검토한다.
- 초기 버전은 상세 비활성화를 제공하고 물리 삭제는 제공하지 않는 방안을 기본으로 한다. 그룹 삭제도 초기 범위에서 제외한다.
- 비활성화는 기존 참조 데이터를 제거하지 않는다. 기존 데이터의 코드명 조회는 계속 가능해야 한다.

### 조회와 API 방향

다음 경로는 신규 API의 제안안이며, 기존 응답 래퍼와 DTO 패턴을 사용한다. 엔티티를 응답으로 직접 반환하지 않는다.

| 용도 | 제안 API | 조회 내용 |
| --- | --- | --- |
| 그룹 목록 | `GET /v1/code-groups` | 그룹 목록 |
| 최상위 상세 | `GET /v1/code-groups/{groupId}/details` | 해당 그룹에서 부모가 없는 상세 |
| 자식 상세 | `GET /v1/code-groups/{groupId}/details?parentId={detailId}` | 해당 부모의 직계 자식 |
| 그룹 생성·수정 | `POST /v1/code-groups`, `PATCH /v1/code-groups/{groupId}` | 그룹 등록, 이름·순서 수정 |
| 상세 생성·수정 | `POST /v1/code-groups/{groupId}/details`, `PATCH /v1/code-groups/{groupId}/details/{detailId}` | 상세 등록·수정·비활성화 |

조회 순서는 `sortOrder ASC, id ASC`로 고정한다. 전달받은 부모나 상세가 경로의 그룹에 속하는지 확인한다.

CMS 관리 조회에는 비활성 항목도 포함한다. 업무 화면의 선택 목록에는 활성 항목만 제공하며, 비활성 조상의 하위 항목도 제외한다. 고객 화면은 일반적으로 필요한 그룹을 업무 코드로 지정하여 상세 선택 목록을 바로 보여준다. 고객용 API는 실제 사용 화면이 생길 때 추가한다.

새 그룹을 등록하는 것만으로 해당 그룹을 사용하는 업무 기능이나 화면이 생성되지는 않는다. 사용하는 서비스에서 대상 그룹과 허용되는 선택 항목을 검증해야 한다.

### 후속 확장 검토 조건

다음 항목은 초기 엔티티, API, 구현 단계에 포함하지 않는다. 필요성이 확인되면 해당 설계와 검증 기준을 함께 추가한다.

#### enum 표시 정보

- 운영자가 상태 표시명이나 배지 색상 등을 배포 없이 변경해야 하는 요구가 생길 때 검토한다. 화면에 enum 목록을 제공하는 것만 필요하다면 읽기 전용 조회로 충분하다.
- 상태의 의미, 허용 값, 전이 규칙은 enum과 도메인 로직이 계속 결정한다. 표시 정보의 변경·누락·비활성화가 주문 처리나 권한 판단을 바꾸어서는 안 된다.
- 도입 시 enum 항목과 표시 정보의 연결 키, enum 추가·변경에 따른 데이터 반영, 표시 정보 누락 시 기본값을 정의한다. `systemCode` 플래그만으로 이 문제들이 해결되는 것은 아니다.
- 검증에는 표시 정보가 없거나 변경되어도 업무 동작이 동일한지, enum에 없는 항목의 등록을 거절하는지 포함한다.

#### 추가 속성

- 설명, 표시 색상, 외부 연동 코드가 필요하면 실제 사용처에 맞는 이름·타입·검증 규칙을 정의한다. `description`도 용도가 확인될 때 추가한다.
- `extraValue1`, `extraValue2`처럼 그룹마다 의미가 달라지는 필드는 사용하지 않는다. 속성이 특정 업무에만 속하면 해당 도메인의 엔티티로 분리한다.
- 배송비 귀책처럼 금액 계산이나 처리 분기에 영향을 주는 값은 표시 메타데이터와 구분하고, 해당 업무의 정책으로 설계한다.

#### 캐싱

- 실제 조회 부하와 응답 시간을 확인하고, 허용 가능한 데이터 반영 지연을 정한 후 도입 여부를 결정한다.
- `admin-api`와 `user-api`는 별도 애플리케이션이다. 로컬 캐시에서는 관리자 서버의 `@CacheEvict`가 사용자 서버의 캐시를 제거하지 못하므로, 어노테이션 적용만으로 무효화가 완료된다고 가정하지 않는다.
- 도입 시 공유 캐시 또는 서버 간 무효화 전달 방식, 트랜잭션 커밋 후 무효화, 전달 실패 시 만료·복구 기준을 정한다. 조회 조건과 관리용·선택용 결과가 섞이지 않도록 캐시 키를 설계한다.
- 조상 비활성화나 부모 변경은 하위 선택 목록에도 영향을 주므로 해당 결과까지 무효화한다. 모든 사용자 서버에서 변경이 정해진 시간 안에 반영되는지 검증한다.

## 4. 메뉴와 관리자 권한

### 메뉴 도메인

메뉴는 공통 코드와 별개의 `Menu` 엔티티로 관리한다. 이름, 경로, 부모, 정렬 순서, 활성 여부를 기본 속성으로 제안한다. 메뉴 계층은 `Menu.parent` 자기참조로 표현한다.

관리 화면의 전체 메뉴 구성 조회와 로그인 관리자의 노출 메뉴 조회를 구분한다. 메뉴를 숨기는 것만으로 API 접근이 차단되지는 않으므로 서버의 기능 권한 검증을 별도로 적용한다.

### 역할과 권한 모델 제안

| 모델 | 책임 |
| --- | --- |
| `PermissionType` enum | `PRODUCT_READ`, `PRODUCT_WRITE` 등 코드가 처리할 수 있는 권한 의미 정의 |
| `Role` | 운영자가 관리하는 역할 |
| `RolePermission` | 역할에 부여한 권한 조합 |
| `AdminRole` | 관리자 계정에 부여한 역할 |

메뉴 노출과 API 인가는 동일한 권한 집합을 기준으로 판단한다. 권한 목록 자체는 enum으로 정의하되, 역할과 권한의 조합은 DB에서 관리하는 방안을 추천한다. 메뉴 노출 결과를 API 권한 검증의 근거로 사용하지 않는다.

### 현재 구현에 미치는 영향

현재 `Admin.role`은 단일 `AdminRoleType`이며, 관리자 로그인과 `JwtPayload.authority`도 단일 권한 문자열을 전제로 한다. 기존 관리 API는 `hasRole('ADMIN')` 등을 사용한다.

동적 역할 관리는 엔티티 추가만으로 완료되지 않는다. 역할 데이터 이관, 로그인 권한 구성, JWT 처리, API 인가, 관리자 가입 시 역할 지정 정책까지 연결해서 설계해야 한다. 사용자 인증과 공유하는 `core`를 변경할 때는 `user-api`의 동작도 검증한다.

### 권한 구현 전에 결정할 사항

- 관리자당 단일 역할 또는 다중 역할 허용 여부.
- 메뉴별 요구 권한과 기능 권한의 연결 방식, 여러 권한의 AND/OR 기준.
- 하위 메뉴만 접근 가능할 때 상위 컨테이너의 노출 방식과 비활성 상위 메뉴 처리.
- 역할 변경·회수의 반영 시점과 기존 JWT 처리 방식.
- 역할·권한 할당을 변경할 수 있는 관리자 범위와 초기 관리자 접근 보호 정책.
- 기존 `ADMIN`, `SELLER` 데이터 및 기존 관리 API 접근 권한의 이관 규칙.

위 항목은 아직 합의되지 않았으며, 문서의 모델 제안만으로 구현을 확정하지 않는다.

## 5. 상품·페이지와 enum 경계

| 대상 | 방향 |
| --- | --- |
| 주문·상품 상태 | enum 유지. CMS는 서버가 허용하는 업무 동작을 요청한다. |
| 주소 형식·파일 유형·토큰·예외 | 시스템 의미를 정의하는 enum 유지. |
| 성별 | 운영 관리 요구가 없으므로 우선 enum 유지. |
| 관리자 역할 | 동적 역할 관리 요구에 따라 전용 모델로 확장하며, 권한의 의미는 코드에서 정의한다. |
| 상품 카테고리 | 운영 중 추가·수정이 필요하면 전용 `ProductCategory` 엔티티로 전환한다. |
| 상품·상품 옵션 | 기존 도메인과 `OptionTemplate` 구조를 재사용한다. |
| 콘텐츠 페이지 | `page` 도메인으로 구분한다. 편집·발행·버전 관리 요구는 후속 설계한다. |

상품 카테고리 전환 시 기존 enum 값을 초기 데이터로 이관하고 상품과 연결한다. 상품 등록·검색·응답 DTO도 enum을 사용하므로 API 호환성과 기존 클라이언트의 변경을 함께 계획한다.

페이지는 독립 도메인 위치만 정한다. 본문 형식, 편집기, 발행 정책, 버전 이력은 현재 요구에 포함되지 않았으므로 임의로 구현 범위를 늘리지 않는다.

## 6. 구현 순서와 검증

| 단계 | 작업 | 완료 검증 |
| --- | --- | --- |
| 1. 코드 관리 | 엔티티, Repository 포트·어댑터, 서비스, 관리 API | 그룹·하위 목록 조회, 중복 코드 거절, 정렬, 부모 그룹 검증, 순환 방지, 비활성 처리 |
| 2. 역할·권한 | 미확정 정책 결정 후 기존 인증·인가 흐름과 연결 | 무권한 직접 API 요청 거절, 역할 변경 반영, 기존 관리자 접근 유지 |
| 3. 메뉴 관리 | 메뉴 구성과 로그인 관리자별 노출 | 계층 구성, 상위 컨테이너 표시, 비활성 메뉴 처리, 기능 권한과 일치 |
| 4. 상품·페이지 확장 | 카테고리 이관, 페이지 요구 상세화 | 기존 상품 연결 보존과 API 호환성 검증, 페이지 인수 조건 확정 |

1단계 관리 API도 기존 관리자 인증·인가로 보호하고, 2단계에서 세부 권한 체계로 연결한다.

enum 표시 정보, 범용 확장 필드, 캐싱은 위 단계의 선행 조건이 아니다. 후속 검토 항목을 채택할 때는 엔티티·API·변경 정책·검증 계획을 함께 갱신한다.

테스트는 도메인 규칙 중심 테스트와 기존 PostgreSQL Testcontainers 통합 테스트 패턴을 사용한다. DB 테스트에는 유일 제약, FK 연결, 계층 변경, 실제 조회 결과를 포함한다. 인증·인가 변경 시 `admin-api`뿐 아니라 공유 보안을 사용하는 `user-api`의 회귀를 확인한다.

역할 및 카테고리 데이터 이관은 현재 `ddl-auto: update`에 맡기지 않는다. 별도 이관 절차에서 기존 값 매핑, 누락·중복 검사, 배포 순서, 실패 시 복구 방법을 준비한다. 이관 도구와 실행 방식은 해당 단계에서 현재 운영 환경을 확인하여 결정한다.

## 7. 문서 완료 기준

- 대화에서 정한 방향과 추가 제안, 미확정 정책을 구분한다.
- 실제 모듈 경계와 Repository 포트·어댑터 패턴을 반영한다.
- 코드 그룹·상세 관계, 자기참조, 조회 방식, 활성 정책을 설명한다.
- 메뉴 노출과 서버 인가를 구분하고 현재 인증 구조의 전환 영향을 기록한다.
- 구현 순서와 단계별 검증 기준을 명시한다.
- 초기 범위에서 제외한 확장 제안은 도입 조건과 검증 과제를 함께 기록한다.
- 이 문서 작성으로 기능 구현이나 DB 변경이 완료되었다고 표현하지 않는다.
